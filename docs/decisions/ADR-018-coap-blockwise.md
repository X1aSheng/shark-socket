# ADR-018:CoAP 分块下发按请求重建响应体

状态:已采纳

## 背景

对比报告 (`COMPARISON-261018-OSS-PEERS.md`) 的 C3 项:

> 全仓 `Block1`/`Block2` 检索 0 命中; `coap/message.go` 无对应 option 定义.
> LwM2M 固件对象 (/5) 与大型 TLV 不可用; Leshan 等标准客户端对大 payload
> 默认走 block-wise, 互联会直接失败.

具体地说, 本仓库的 CoAP 服务端只能把响应体塞进**一个**数据报. 这在两端都是
硬约束: 服务端受 `MaxDatagram` (默认 64 KiB) 限制, 网络受路径 MTU 限制.
超过 MTU 的数据报靠 IP 分片, 而 IP 分片在丢包时的代价是全片重传, 且中间设备
经常直接丢弃. RFC 7959 给出的解法是把 body 切成带编号的块, 每块独立传输.

不做这件事的后果不是"性能差一点", 而是**与标准客户端不互通**: Leshan 之类
的客户端对超过其偏好的 payload 一律先发不带 Block2 的请求, 期望拿到 M=1 的首块;
如果收到一个 4 KiB 的巨型数据报被 IP 分片, 行为取决于中间网络.

## 决策

1. **只做 Block2(下发), Block1(上传)明确拒绝.** Block1 需要按对端累积请求体,
   那是"每传输一块有界缓冲", 与 ADR-017 刚刚清理掉的资源形态同类. 而 LwM2M
   的上传目前最大也只是几个 TLV, 不构成阻塞.
2. **按请求重建响应体, 不缓存.** 每个块请求都重新调用一次 `Responder`/
   handler, 服务端不持有正在进行的传输状态.
3. **默认关闭, 用 `WithMaxBlockSize(size)` 打开.** 打开后, 超过块大小的响应
   按块下发; 关闭时逐字节与之前一致.
4. **块大小只能向下协商.** 对端要 256 就给 256; 对端要 1024 而服务端上限 512 时
   给 512, 并且按"先用对端大小算偏移, 再按本次大小重新整除"换算块号.
5. **带 Block1 的请求回 `4.13 Request Entity Too Large`**, 并附一个 Block1 提示
   (RFC 7959 sec.2.9.3), 而不是忽略该选项.
6. **观察通知不分块.** `NotifyObservers` 的载荷仍一次性发送.

## 原因

- **为什么无状态.** 缓存响应体意味着服务端要在两次块请求之间持有一块**任意大小**
  的缓冲: 大小由业务决定, 数量由并发读决定, 生命周期由对端决定. 这三件事凑在一起
  就是一个放大攻击面 -- 一个 GET 4 MiB 资源的客户端只付一个请求的代价, 就能让服务端
  分配 4 MiB 并保留到超时. ADR-017 花了一整轮把这种"按对端意愿分配"的形态清掉,
  这里没有理由再引入一个.
- **为什么默认关闭.** Block2 是 **critical** 选项(编号 23). 一个不实现 RFC 7959
  的客户端收到带 Block2 的响应, 按 RFC 7252 sec.5.4.1 必须拒绝整个响应; 也就是说
  默认打开会让"读一个 2 KiB 资源"对老客户端从成功变成失败. 默认关闭时行为改变只能
  由部署者显式触发, 这是可以让运维解释的边界.
- **为什么 1024 是上限.** SZX 字段只有 3 位, 6 就是 1024; 7 被 RFC 7959 sec.2.2
  保留. 1024 的块加上 CoAP 头与选项仍在 1280 字节的 IPv6 最小 MTU 之内, 不需要
  任何分片.
- **为什么拒绝 Block1 而不是忽略.** 忽略 Block1 的后果是每个分片都被当成完整请求体
  交给 handler. 对 LwM2M 的 write/execute 来说, 那是把 `frag1` 当成完整载荷执行了
  一次副作用, 而且客户端看不到任何错误. `4.13` 至少让客户端知道"这条路走不通".
- **为什么观察通知不分块.** 分块传输的后续块由**客户端请求**驱动. 通知是服务端
  主动推送的, 没有可依附的请求; 若要做, 需要为每条观察关系缓存通知体并按请求切片,
  那是决策 2 明确回避的东西. 需要观察大资源时, 正确做法是在注册的 GET 上走分块,
  由客户端自己拉后续块.

## 后果

- **响应体大小不再有单数据报上限**, 只受块数与 `MaxDatagram`(读方向)约束.
  一个 1 MiB 资源 = 1024 次 `Responder` 调用. 这是无状态设计的直接代价, 因此
  handler 应当是纯读或带缓存的; 分块读取不适合"每次调用都写库"的实现.
- **每次响应多一次选项查找与切片**, 打开时测到 `blockFor` 13.70 ns/op / 8 B / 1 alloc
  (那次分配是 `*BlockOption`, 每响应一次), `parseBlockOption` 2.23 ns/op / 0 alloc.
  关闭时只有一次 `MaxBlockSize <= 0` 判断.
- **`MaxBlockSize` 之外的取值会被向下取整到 16..1024 的 2 的幂**: 线上格式只有一个
  3 位指数, 表达不了 700 这样的块大小, 与其在发送时才报错, 不如在配置时就归一.
- **去重表的内存上界反而变小了.** `seen` 记录的是每条 CON 交换的**完整响应字节**,
  以前一条记录可以是 64 KiB (`MaxDatagram`); 打开分块后每条记录最多是一个块,
  即 1 KiB. 最坏情况从 65536 x 64 KiB 降到 65536 x 1 KiB, 代价是同样的资源会占用
  更多条目.
- **Block1 的语义永久缺失**: 本服务端不接受分块上传, 只会回 4.13. 若将来需要,
  必须新增一份按 (对端, token) 索引的有界缓冲, 并在超时后回收, 见重新评估条件.
- **未与标准客户端实机联调.** 验收用例是本仓库自己写的客户端: 4 KiB body 在
  1 KiB 块下按 4 块重组, 请求 256 字节时按 4 块(每块 256)重组, NUM 越界回 4.02,
  关闭时仍是单数据报. Leshan 实机互操作**未做**, 挂账.

## 重新评估条件

- 若 LwM2M 固件升级 (Object 5) 成为需求, Block1 必须实现. 那时需要:
  按 (对端, token) 记录已收到的块与期望的下一块, 单传输缓冲上限固定 (例如 64 KiB),
  并用 EXCHANGE_LIFETIME 回收; 同时要在 `4.08 Request Entity Incomplete` 上区分
  "缺块"与"超限".
- 若观察大资源成为常见用法, 需要为观察关系引入"最近一次通知体"的缓存, 并让它与
  现有 `pendingNotifies` 共用生命周期, 否则通知与块请求会各持一份拷贝.
- 若实测发现 `Responder` 每次重建的成本不可接受 (例如需要读取大文件), 应引入
  按 (对端, token) 的有界单块缓存而不是完整 body 缓存: 只保留"当前块", 下一块
  再重建, 用一次重复计算换掉无界内存.
