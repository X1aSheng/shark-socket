# ADR-015:消除共享热路径上的三项结构性开销

状态:已采纳

## 背景

对比报告 (`COMPARISON-261018-OSS-PEERS.md`) 在 B5, B6, B7 三项上指出: 本项目的
每包/每连接开销里有三处不是来自 I/O, 而是来自被所有传输共享的数据结构本身.

- **B6** UDP 与 CoAP 用 `addr.String()` 作会话表键. 每个数据报都要解析一次会话,
  而 `net.UDPAddr.String()` 内部要分配两次 (`IP.String` 与 `JoinHostPort`),
  再把字符串装箱进 `any` 键. 实测 3 allocs/包, 与 payload 拷贝同量级.
- **B7** 插件链 `snapshot()` 每条消息取一次进程级 `RWMutex` 的读锁, 且每个插件
  各自 `defer/recover`. 读锁本身在单线程下只有几纳秒, 但它是**所有传输, 所有核**
  共用的一个缓存行.
- **B5** `SessionManager` 是全局单表 + 单把 `RWMutex`. TCP, UDP, WebSocket, HTTP,
  QUIC, gRPC-Web, CoAP 的每一次 accept 与 close 都在这一把锁上串行.

前三项 (ADR-012/013/014) 改的是数据面的复制与系统调用; 这三项改的是**共享结构
的争用与分配**, 量级更小但作用于每一条消息和每一个连接, 且随核数放大.

## 决策

1. **B6**: 新增 `shared.PeerKey` (`[16]byte` 地址 + `uint16` 端口 + zone), 代替
   `addr.String()` 作 UDP/CoAP 的会话表键, 并在会话上缓存该键供错误路径复用.
2. **B7**: 插件链改为 `atomic.Pointer[pluginView]` 发布不可变视图, 读路径完全不
   加锁; `OnMessage` 与 `OnAccept` 改为**链级单次 recover** (用下标定位出问题的
   插件), `OnClose`/`StartAll`/`StopAll` 保留逐插件 recover.
3. **B5**: `SessionManager` 按会话 ID 分为 64 个分片, 每片一把 `RWMutex` 和一个
   独立 map, 并按 64 字节对齐; 全局容量改为在共享计数器上 CAS 预留.

## 原因

- **PeerKey 而不是更快的字符串**: 目标是零分配, 不是更短的字符串. 结构体键可比较
  且构造不分配; 装箱进 `any` 的那一次也因接口值未逃逸而被编译器放到栈上, 实测
  归零. 地址统一存 16 字节形式, 使 `1.2.3.4` 与 `::ffff:1.2.3.4` 落到同一个键 --
  否则同一对端会拿到两个会话, 从而绕过每对端的资源上限.
- **为什么保留 `sessions` 这张传输内表**: 报告把"B5 双表"与"全局锁"并列, 但二者
  性质不同. 传输内表按**对端地址**索引, 全局表按**会话 ID** 索引, 键不同, 用途
  不同, 合并需要让全局表支持按地址查找, 是把 UDP 的字符串键搬进全局表的反向改动.
  本次只解决争用 (分片), 双表保留, 理由记录在后果里.
- **链级 recover 的前提是语义不变**: `OnMessage` 的 panic 本来就会中断整条链,
  `OnAccept` 的 panic 本来就会回滚. 把 N 个 defer 合成 1 个不改变任何可观测行为.
  `OnClose` 是例外 -- 它的逐插件 recover 是为了让**后续**插件仍被关闭; 合成一个
  会让一个插件的 panic 拖住后面所有插件的资源, 故保留.
- **容量用 CAS 而不是分片内计数**: 上限是全局语义. 若按片计数, 两片各自都未达
  各自上限, 合起来仍可能超全局上限. 计数器是唯一权威, 用 CAS 认领.
- **判重先于判容量**: 与单表时代的返回顺序保持一致. 传输重试一个已存在的会话 ID
  时, 即使容量已满也必须被告知"重复"而不是"容量", 否则重试语义会变.

## 后果

- **实测** (开发机 Windows, AMD Ryzen 7 8845HS, 16 线程; 单核数字供回归参考):

| 项 | 改前 | 改后 |
| --- | --- | --- |
| UDP 会话解析 | 99-113 ns/包, 32 B, 3 allocs | 46-47 ns/包, 0 B, 0 allocs |
| 插件链 5 插件 (16 并发) | 23.4-24.5 ns/op | 4.5-5.3 ns/op |
| 插件链 + 并发重配置 (16 并发) | 83-97 ns/op | 7-17 ns/op |
| 会话注册/查询/注销 (16 并发) | 366-382 ns/op | 149-163 ns/op |
| 会话注册/查询/注销 (单线程) | 184-194 ns/op | 165-203 ns/op |

  单线程会话管理一项在噪声内持平 (未回退). 三项并发数字是本次的主要收益:
  它们随核数放大, 在 16 核上分别是 4.6 倍, 6 倍, 2.4 倍.

- **数据报路径的剩余分配**: payload 拷贝 (`append([]byte(nil), buf[:n]...)`) 仍在,
  因为读缓冲是复用的, 且 `Send` 契约要求调用方可以立即释放. 每包 4 次分配降到
  1 次, 不是 0 次. 要做到 0 次需要引入缓冲池并改 `OnMessage`/`Send` 的所有权,
  那是 ADR-001 层面的改动.
- **双表保留**: 一个会话仍同时存在于传输内表与全局表. 两表的键与生命周期不同,
  本次不动. 若将来要合并, 需要全局表支持按 (协议, 对端地址) 查找.
- **`Snapshot`/`Range` 不再是时点快照**: 它们逐片取锁, 遍历期间新会话可能落在尚未
  访问的片里. 调用方 (`Broadcast`, `CloseAll`) 只要求"活会话的超集", 且 `CloseAll`
  会循环到空, 故不受影响. 契约已写进注释.
- **插件链的 panic 报告粒度不变**: 仍记录出问题的插件名与 panic 值, 只是由链级
  defer 统一记录.
- 会话表固定 64 片, 每片 64 字节, 共 4 KiB 常驻 -- 与减少的争用相比可忽略.

## 重新评估条件

- 若引入缓冲池并改动 payload 所有权, B6 的剩余一次分配消失, 本 ADR 的数据报
  结论需重述.
- 若传输内表与全局表合并 (全局表支持按地址查找), B5 的"双表保留"一节失效.
- 若插件链将来支持移除插件 (现在只能追加), 视图发布路径需要重新检查.
