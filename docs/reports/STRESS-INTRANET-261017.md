## 1. 结论摘要 TL;DR

1. **公网压测的 80k 崩塌是带宽造成的, 不是服务端能力问题。** 同一份代码改走内网后,
   80k 档达成率从 **63.1% 提升到 98.2%**, p99 从 212 ms 降到 50 ms。
   前一报告保留的"归因不确定"现已解决。
2. **内网真实承载能力: 80k msg/s 稳定, 120k msg/s 崩塌。**
   80k 达成率 98.2%, p50 3.43 ms, p99 50 ms, 尾比 14.58;
   120k 档达成率崩到 **0.7%**, 且第 2 秒起完全停摆。
3. **弹性池没有优于固定池, 且找到了确切原因。** 三组对照 (内网, 同一阶梯):
   80k 档吞吐 fixed-2 = 42k, **elastic-2-16 = 48k**, fixed-4 = 50k。
   弹性池**优于最低档位 14.3%, 但仍低于固定 4 worker 5.5%**。
4. **根因: 弹性池实测只在 2-4 worker 间波动, 从未触及上限 16。**
   70 次服务端采样: workers=2 占 56%, workers=3 占 3%, workers=4 占 41%。
   扩容机制在工作, 但在 2 核机器上**没有可用的上调空间**。
5. **一个可能的设计局限被识别出来**: `maybeScale` 仅在 Submit 路径触发
   (`scaleCheckInterval=1024`)。队列满时提交被拒绝, 恰好是最需要扩容的时刻,
   扩容判定却随提交停止而停止。这解释了为何池稳定在刚好不崩塌的最低档位。

## 2. 为何必须内网重测

前一报告 (`STRESS-LADDER-261017`) 的第 8 节明确记录: 80k msg/s 需要 333 Mbps
线缆流量, 是阿里云标称 100 Mbps 的 3.3 倍, **该档崩塌无法排除带宽因素**,
因此把"服务端真实上限"标为未测定。

本轮把两台主机置于**同 VPC 内网** (172.29.176.0/20), 实测 RTT 0.080 ms,
带宽不再受公网配额约束。两个变量 (带宽、处理能力) 中的带宽被消除后,
服务端能力可以被单独测量。

前序报告的核心待办正是这一项, 本轮完成。

## 3. 内网承载能力重测 (固定池 4 worker)

### 3.1 测试条件

| 项 | 值 |
|---|---|
| 服务端 | srv3 内网 172.29.189.108, TCP echo |
| 生成端 | srv2 内网 172.29.189.109 (独立物理机) |
| RTT | 0.080 ms (公网约 1-3 ms) |
| 连接数 | 50 |
| payload | 256 B |
| 每档时长 | 10 s |
| 供给阶梯 | 20k / 40k / 80k / 120k msg/s |
| 服务端配置 | 固定 4 worker, 队列 512, PolicyDrop |

### 3.2 结果

| 供给 | 达成率 | 实测 (msg/s) | p50 | p99 | 尾比 |
|---|---|---|---|---|---|
| 20,000 | 0.995 | 19,898 | 76 us | 1.30 ms | 17.03 |
| 40,000 | 0.995 | 39,781 | 1.163 ms | 4.053 ms | 3.49 |
| 80,000 | **0.982** | **78,521** | 3.429 ms | 49.987 ms | 14.58 |
| **120,000** | **0.007** | **790** | 93 us | 51.476 ms | 553.65 |

### 3.3 120k 档的崩塌形态

```
  1  15120   7783      <- 第一秒即开始丢
  2    240    120
  3      0      0      <- 完全停摆
  4-9    0      0
  10     0      0
```

与公网的 80k 崩塌 (第 1 秒 79840, 第 2 秒 53509, 之后稳定在 44-49k) 形态
**完全不同**: 公网是"降级到新稳态", 内网 120k 是**"停摆"**。
`errs=50` 表示 50 条连接全部报错, 连接本身被拒绝而非排队。

这个差异有诊断价值: 公网 80k 的"部分降级"是链路排队造成的背压,
内网 120k 的"完全停摆"则是服务端在接收侧直接拒绝。

### 3.4 公网与内网对照

| 档位 | 公网达成率 | 内网达成率 | 公网 p99 | 内网 p99 |
|---|---|---|---|---|
| 20,000 | 0.995 | 0.995 | 1.223 ms | 1.30 ms |
| 40,000 | 0.995 | 0.995 | 1.308 ms | 4.053 ms |
| 80,000 | **0.631** | **0.982** | **212.522 ms** | **49.987 ms** |
| 120,000 | 未测 | **0.007** | - | 51.476 ms |

**80k 档达成率从 63.1% 提升到 98.2%, p99 从 212 ms 降到 50 ms (4.2 倍)。**
这是"80k 崩塌是带宽所致"这一判断的直接证据: 代码未变, 只换链路, 结果天差地别。

40k 档 p99 内网 (4.053 ms) 高于公网 (1.308 ms), 因为内网 RTT 更低, 客户端
发送节奏更快, 服务端队列填充更快, 排队延迟因此更高。这是正常现象:
**低 RTT 使系统更早进入饱和状态**。

### 3.5 服务端侧印证

固定池服务端 STATS 采样 (每秒一次, 本轮新增 `-stats-interval` 参数):

```
STATS goroutines=108 workers=4 bounds=(4,4) heapAllocMiB=3.0 numGC=1
STATS goroutines=108 workers=4 bounds=(4,4) heapAllocMiB=3.7 numGC=10
STATS goroutines=108 workers=4 bounds=(4,4) heapAllocMiB=0.7 numGC=14
```

`workers=4 bounds=(4,4)` 确认固定池配置生效。

## 4. 弹性池与固定池对比

### 4.1 为什么需要三组对照

只比较"弹性池 vs 固定池"是不够的: 弹性池从 `minWorker=2` 起步, 固定池用的是
4 worker。若不固定可比起点, 差异会同时包含"弹性机制"与"起始 worker 数"两个
因素。因此本轮设三组:

- **fixed-2**: 固定 2 worker, 作为最低档位基线
- **fixed-4**: 固定 4 worker, 前序报告的默认配置
- **elastic-2-16**: 弹性池, 范围 [2, 16], 起步 2

三组除 worker 配置外完全一致。

### 4.2 结果对比

达成率:

| 供给 | fixed-2 | fixed-4 | elastic-2-16 |
|---|---|---|---|
| 20,000 | 0.995 | 0.995 | 0.995 |
| 40,000 | 0.993 | 0.995 | 0.993 |
| 80,000 | 0.958 | **0.982** | 0.971 |

80k 档明细 (最能区分三者):

| 配置 | 实测吞吐 | 尾比 p99/p50 |
|---|---|---|
| fixed-2 | 42,000 msg/s | 15.53 |
| **elastic-2-16** | **48,000 msg/s** | 14.70 |
| fixed-4 | 50,000 msg/s | 13.10 |

### 4.3 核心结论

以 fixed-2 为基线:

| 配置 | 80k 吞吐 | 相对提升 |
|---|---|---|
| fixed-2 (基线) | 42,000 | - |
| elastic-2-16 | 48,000 | **+14.3%** |
| fixed-4 | 50,000 | +19.0% |

**弹性池确实带来了提升, 但仍低于固定 4 worker。** 它落在两者之间。

这与 `CLOUD-VALIDATION-261016-SRV23` 第 5.3 节的方向一致 (12000/s 供给下
弹性池多投递 54.0%), 但本轮实测的差距远小于该报告的量级。差异的原因见下一节。

### 4.4 根因: 弹性池从未真正扩容

服务端 STATS 采样 (70 次) 的 worker 数分布:

| workers | 采样次数 | 占比 |
|---|---|---|
| 2 | 39 | 56% |
| 3 | 2 | 3% |
| 4 | 29 | 41% |

`bounds=(2,16)`, 但**实测从未超过 4 个 worker**。上限 16 中有 12 个从未被使用。

因此弹性池的表现几乎完全由"它恰好爬到了 4"决定, 而不是由 16 的上限决定。
它优于 fixed-2 是因为爬升到了 4; 略逊于 fixed-4 是因为并非**始终**是 4
(56% 的时间停留在 2)。

**这是一个在 2 核机器上会出现的必然结果**: GOMAXPROCS=2, 超过 4-8 个 worker
的边际收益迅速递减, 即使扩容到 16 也换不来吞吐量。

### 4.5 一个被识别出的设计局限

`internal/transport/shared/pool_scalable.go` 的扩容判定只在 Submit 路径上触发:

```go
func (p *ScalablePool) Submit(sess core.Session, protocol core.Protocol, payload []byte) error {
    err := p.submit(sess, protocol, payload)
    if p.submitTick.Add(1)%scaleCheckInterval == 0 {
        p.maybeScale()
    }
    return err
}
```

代码注释 (第 161-163 行) 明确说明了这个设计意图:

> Every return path ticks, including ErrWriteQueueFull: a rejected submit is
> the single strongest signal that the pool is short of workers, so it must
> not be skipped.

意图是: 提交被拒绝 (`ErrWriteQueueFull`) 恰恰是池子缺 worker 的最强信号,
所以拒绝路径也要触发扩容判定。

但这里存在一个结构性问题: **队列满时, 提交会被持续拒绝, 而扩容判定依赖于
提交这个动作本身**。如果拒绝率高到提交几乎不发生, `submitTick` 的推进也随之
放缓, 扩容检查的频率下降。第 197 行的 `occupancy = len(queue)/cap(queue)`
虽然能读到满队列, 但读取它需要先有一次 Submit 调用。

本轮的观测与此一致: 池稳定在刚好不崩塌的最低档位 (2-4), 而非爬到上限。

**这不构成缺陷判定**, 因为:
1. 机制确实在工作 (worker 数在 2-4 之间确实随负载变化);
2. 在 2 核机器上, 即使修复这一点, 上限 16 也无空间可涨;
3. 是否有价值需在多核环境重测才能判断。

但它是一个**已识别的、值得在多核环境验证的假设**。

## 6. 结论汇总

| 问题 | 答案 | 可靠度 |
|---|---|---|
| 公网 80k 崩塌是服务端能力问题吗? | **不是, 是带宽所致** | 高: 同代码换链路, 达成率 63.1% -> 98.2% |
| 内网承载能力 | **80k msg/s 稳定 (98.2%), 120k 崩塌 (0.7%)** | 高 |
| 弹性池优于固定池吗? | **是但有限: +14.3%, 仍低于 fixed-4 5.5%** | 高 (三组对照) |
| 弹性池为何未达上限? | **实测只用到 2-4 worker, 2 核环境无上调空间** | 高 (70 次采样) |

**给容量规划的结论**: 2 vCPU 节点的 TCP echo 承载约 80k msg/s (256 B, 内网)。
超过此值应提高 worker 数 (固定池优于弹性池, 因后者在本环境无法有效扩容),
或在更高规格的节点上分散负载。

## 8. 数据可信度与边界

- **本轮数据为单次运行**, 各档内部一致但未做跨轮重复。承载能力数值应至少
  `-count=3` 复采后再作为容量基线。
- **2 vCPU 是小型规格**。80k 是这台机器的上限, 不是框架的上限。
  多核环境的承载能力与 worker 最优值均需重测。
- **本轮仅测 TCP echo, 50 连接, 256 B payload**。UDP / WebSocket / HTTP /
  gRPC-Web / QUIC 的承载形态不同, 不应外推。
- **内网 RTT 0.080 ms 极低**, 使系统更快进入饱和状态。生产环境的 RTT 更高,
  因此实际可承载的连接数可能低于本轮结果。
- **弹性池的 worker 数由服务端 STATS 采样得出**, 采样间隔 1 秒。10 秒窗口下
  共 70 次采样, 若池在亚秒尺度上快速伸缩, 该采样可能遗漏极值。
- 第 4.5 节关于扩容触发局限的分析是**基于代码审阅与观测数据的推断**, 未做
  针对性实验验证。表述为"值得验证的假设"而非结论。
