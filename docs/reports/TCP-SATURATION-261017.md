## 1. 结论摘要 TL;DR

1. **TCP 饱和点 = 142,000 msg/s** (256 B payload, 50 连接, 2 vCPU 服务端)。
   这是达成率 0.995 的最后一个健康档位; 145,000 起持续下降, 180,000 时降至 0.728。
2. **瓶颈是每消息处理成本, 不是带宽也不是连接数。** 两个维度实验给出决定性证据:
   - payload 从 64 B 增至 1024 B (字节数 16 倍), 吞吐仅降 **9.6%**。
     若是带宽瓶颈, 应降约 16 倍。
   - 连接数 10 -> 50 提升 40%, 50 -> 200 **无增益**。连接数不是限制因素。
3. **饱和时是背压, 不是崩塌。** `errs=0` 且 `recv == sent` (906,400 完全相等),
   每秒稳定在 141k-152k, p50 296-303 us 无劣化, 尾比稳定 3.3-3.9。
   服务端未丢弃任何消息, 是同步请求-响应的生成器被响应速度拖慢。
   服务端侧同样干净: `sessions_accepted == sessions_closed`, 无任务队列拒绝。
   **达成率低于 1 在健康区间内是背压的表现, 与崩塌有明确区别** (3.4 节有对照表)。
4. **服务端的实际稳态吞吐约 145,000-150,000 msg/s**, 无论供给多少。
   多档独立复现: 145,067 / 145,867 / 146,831 / 150,008 / 150,833 msg/s。
5. **两侧 CPU 均未跑满** (load average < 1, 2 核), 说明限制来自串行化路径
   而非总算力。145k msg/s 意味着每条消息约 4 次 syscall, 合计约 58 万次/秒,
   这在 2 核上接近上限。

## 2. 饱和点测定过程

采用三阶段收敛, 每阶段依据上一阶段的结果收窄区间。

### 2.1 第一阶段: 粗扫 (80k / 120k / 180k)

| 供给 (msg/s) | 达成率 | 实测 (msg/s) | p50 | p99 | 尾比 |
|---|---|---|---|---|---|
| 80,000 | 0.994 | 79,500 | 295 us | 994 us | 3.37 |
| 120,000 | 0.994 | 119,250 | 291 us | 954 us | 3.28 |
| 180,000 | 0.833 | 150,008 | 294 us | 967 us | 3.29 |

180k 档的秒级序列显示拐点形态:

```
  8  145977  145977     <- 第 8 秒已封顶
  9    3783    3783     <- 剩余时间仅 3783
 10       0       0
```

即服务端在第 8 秒达到 145,977 msg/s 后无法继续, 供给剩余部分全部丢弃。
**拐点在 120k-180k 之间。**

### 2.2 第二阶段: 收窄 (140k / 150k / 160k)

| 供给 | 达成率 | 实测 (msg/s) |
|---|---|---|
| 140,000 | 0.994 | 139,125 |
| 150,000 | 0.979 | 146,831 |
| 160,000 | 0.904 | 144,680 |

150k 起达成率跌破 0.98, **拐点在 140k-150k 之间**。

### 2.3 第三阶段: 收敛 (142k / 145k / 148k, 10 秒档)

| 供给 | 达成率 | 实测 (msg/s) | p50 | p999 | max |
|---|---|---|---|---|---|
| **142,000** | **0.995** | **141,290** | 296 us | 2.599 ms | 4.083 ms |
| 145,000 | 0.983 | 142,564 | 297 us | 2.549 ms | 4.104 ms |
| 148,000 | 0.980 | 145,055 | 303 us | 2.591 ms | 10.363 ms |

**142,000 msg/s 是达成率 >= 0.99 的上限。**

### 2.4 稳态吞吐的复现性

五次独立运行给出的服务端稳态吞吐:

| 运行条件 | 实测吞吐 (msg/s) |
|---|---|
| 供给 145k, 50 连接, 256 B | 145,067 |
| 供给 200k, 50 连接, 256 B | 145,867 |
| 供给 150k, 50 连接, 256 B | 146,831 |
| 供给 180k, 50 连接, 256 B | 150,008 |
| 供给 200k, 50 连接, 64 B | 150,833 |

集中在 **145k-151k**, 离散度约 3.8%。这说明 145k 不是某一档的偶然值,
而是服务端的实际吞吐上限。

## 3. 瓶颈定性: 为什么不是带宽, 也不是连接数

达成率下降有两种常见解释: 带宽饱和, 或服务端处理能力饱和。
区分它们需要改变"每消息字节数"或"并发连接数", 观察吞吐如何响应。

### 3.1 payload 维度 (连接数固定 50, 供给固定 200k)

| payload | 实测吞吐 (msg/s) | 相对 64 B |
|---|---|---|
| 64 B | 150,833 | 基线 |
| 256 B | 145,067 | -3.8% |
| 1024 B | 136,400 | -9.6% |

**字节数增加 16 倍, 吞吐只降 9.6%。**

若为带宽瓶颈, 吞吐应与字节数成反比: 1024 B 的吞吐应约为 64 B 的 1/16
(约 9,400 msg/s)。实测 136,400 是基线的 90%, 因此**带宽有裕量**。

线缆流量核算 (双向): 145,000 msg/s x 520 B x 8 bit = 603 Mbps。
内网链路承载得住这个量级, 所以带宽不是限制因素。

### 3.2 连接数维度 (payload 固定 256 B, 供给固定 200k)

| 连接数 | 实测吞吐 (msg/s) | 相对 10 连接 |
|---|---|---|
| 10 | 103,833 | 基线 |
| 50 | 145,867 | +40.5% |
| 200 | 141,108 | +35.9% |

10 -> 50 连接提升 40%, 说明**低连接数时每连接的往返延迟成为限制**。
50 -> 200 连接不再提升 (反而略降 3.3%), 说明**并发连接数不是瓶颈**,
服务端在 50 连接已达到其并行处理上限。

### 3.3 结论

两个维度共同排除:

| 假设 | 排除依据 |
|---|---|
| 带宽瓶颈 | payload 16 倍仅降 9.6% |
| 连接数瓶颈 | 50 -> 200 连接无增益 |
| **每消息处理成本** | **以上均排除, 是唯一符合的解释** |

每条消息的服务端路径: `read()` -> 长度前缀解析 -> 插件链 `OnMessage`
-> handler -> `write()` -> goroutine 调度。145,000 msg/s 意味着每条约
4 次 syscall (客户端 2 + 服务端 2), 合计约 58 万次/秒。

### 3.4 一个需要说明的现象: 达成率下降但零丢失

饱和时 p50 几乎不变 (296 us -> 303 us), 尾比稳定在 3.3-3.9, 这与
"服务端队列溢出"的经典形态不符, 后者通常伴随 p50 显著抬升。

在 200,000 msg/s 供给下复测, 结果是:

```
sent=906400  recv=906400  errs=0        <- 收发完全相等, 零错误
per_second:
  1  141741  141741
  2  151107  151107
  3  152861  152861
  4  152303  152303
achieved_ratio=0.755 (achieved 151067/s)
```

**`errs=0` 且 `recv == sent`**: 每一条发出的消息都收到了回显, 没有任何超时或
丢弃。达成率低于 1 的原因不是服务端拒绝, 而是**背压**:

生成器是同步请求-响应模型 (`Exchange` 内写完等回包)。当供给 200k 高于服务端
能力 151k 时, 发送节奏被服务端的响应速度自然拖慢, 每秒实际完成 141k-152k
次交换。**服务端没有丢弃任何东西, 是客户端自己降到了它能承受的速率。**

这一点必须与"崩塌"区分开:

| | 本轮观察 | 真正的崩塌 |
|---|---|---|
| errs | 0 | 大量超时或连接重置 |
| recv/sent | 相等 | 明显小于 |
| p50 | 稳定 (296-303 us) | 显著抬升 |
| 尾比 | 稳定 (3.3-3.9) | 急剧上升 |
| 秒级序列 | 平稳 (141k-152k) | 断崖后新稳态 |

服务端侧数据同样支持这个判断:

```
sessions_accepted_total 534135
sessions_closed_total   534135      <- 完全相等, 零泄漏
sessions_active         0
(无 tcp_task_queue_full 指标出现)
```

**所以"达成率下降"在健康区间内是背压的表现, 不代表服务端在丢消息。**
容量拐点的判断不受影响 (142k 仍是服务端能力上限), 但机制的描述必须准确。

## 5. 给容量规划的数字

以本轮实测为准 (2 vCPU, 50 连接, 256 B payload, 内网):

| 用途 | 建议值 |
|---|---|
| **容量上限 (拐点)** | **142,000 msg/s** |
| 稳态吞吐 (服务端自发) | 145,000-151,000 msg/s |
| 安全运行目标 (80% 拐点) | ~113,000 msg/s |
| 单节点跨协议 (见 PROTOCOL-CAPACITY) | 60k 时所有协议均 0.992 |

注意事项:

- **这些是 2 vCPU 的数字。** 更高规格的节点拐点会更高, 且可能从
  "每消息成本受限" 转为 "CPU 受限"。
- **60k 档所有协议均未饱和**, 本轮的 TCP 拐点 (142k) 大概率也高于其他协议
  在同等条件下的拐点, 但 WS/HTTP/gRPC-Web 复用连接, 每消息成本不同,
  不能直接套用。
- **字节数影响有限但非零**: 64 B -> 1024 B 吞吐降 9.6%, 若实际负载是大包,
  应按 136k 而非 150k 估算。

## 6. 数据可信度与边界

- **单次运行, 未做跨轮重复**。但五档独立的稳态吞吐离散度仅 3.8%,
  重复性可接受。
- **10 秒档位, 每档样本有限**。142k 档 1,412,900 次交互, 统计上充分。
- **采样上限触发**: 所有 200k 样本档位均标记 `latency_samples_capped=true`
  (200,000 上限), 分位数字描述的是前半段。因饱和前延迟稳定, 该截断不影响
  拐点定位, 但 p999 与 max 应视为下界。
- **服务端为默认配置** (未调 worker 数与队列大小)。调优后拐点会移动,
  本报告不覆盖调优后的数值。
- **仅 TCP**。UDP / WebSocket / HTTP / CoAP / gRPC-Web 的拐点未测。
- **2 vCPU 单节点**。多节点或更高规格需重新测定。
