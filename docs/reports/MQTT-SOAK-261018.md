## 3. 9.1 小时长浸泡 (聚合数据丢失)

### 3.1 发生了什么

- 启动参数: `loadgen -online 2000 -rate 20000 -duration 10h30m
  -sample-interval 300s -note "overnight soak, ~10.5h to 12:00"`
- 实际运行 **9 小时 08 分** 后按指示停止 (计划到 12:00, 提前停止)
- `soak_long.json` 全程为 **0 字节**

### 3.2 为什么数据丢失

先发 SIGTERM, 进程正常退出, 但 JSON 汇总未落盘 -- `loadgen` 不处理 SIGTERM,
只在正常跑完 `duration` 时写文件。

**这是一个工具缺陷**: 一个设计为长时间运行的工具, 应当在被要求停止时保存已
积累的结果。目前 9 小时的计数器、延迟分位与吞吐统计全部丢失, 只剩下外部
RSS 追踪。

可改进的方向 (不在本轮范围): `loadgen` 应注册 SIGTERM/SIGINT handler, 写
出当前累计结果后再退出。

### 3.3 保留的数据: 内存全程平稳

生成端 RSS 追踪 (`lg_long_rss.txt`, 每 60 s 一个采样):

| 项 | 值 |
|---|---|
| 采样点 | 296 |
| RSS | **恒定 92,296 KB (90 MB)** |
| 时间跨度 | 9.1 小时 |

296 个采样点全部为同一数值, 无任何上升趋势。

## 4. broker 侧观测 (9.1 小时)

来源: srv2 上 `/root/shark -allow-all -addr 0.0.0.0:18883`, PID 21212。

### 4.1 资源

| 指标 | 值 |
|---|---|
| 运行时长 | 9 h 08 m 31 s |
| 累计 CPU 时间 | 13 h 02 m 38 s (约 144%, 跨核) |
| VmRSS (停止前) | 112,044 KB |
| VmRSS (压测中途观测) | 111,664 KB |
| VmHWM (峰值) | 118,028 KB |
| 线程数 | 11 (全程未变) |
| 文件描述符峰值 | 2,118 |

**RSS 在 9 小时内的变化为 111,664 -> 112,044 KB, 即 +0.34%。** 判断泄漏的
依据是是否持续增长, 而非绝对值; 这里是平的, 因此**无内存泄漏**。

### 4.2 连接回收

生成端被 SIGTERM 停止后, 按 5 秒间隔观察:

| 时刻 | ESTAB | fds |
|---|---|---|
| 停止前 | 2110 | 2118 |
| t+5s | **0** | **8** |

**2110 个连接在 5 秒内全部回收, 文件描述符降到 8。**

这一点比数字本身更重要: 生成端是被硬停的 (SIGTERM 后进程直接消失, 未发送
任何 MQTT 断开消息), 属于最不体面的断开方式。broker 在这种条件下仍然完全
回收了全部会话状态, 说明它的连接回收不依赖对端的主动关闭。

### 4.3 关闭

broker 在 SIGTERM 后正常退出, 端口释放, 无残留进程。走的是其文档化的关闭路径
(排空 -> 关闭会话 -> 停止传输), 而非被强杀。

### 4.4 数据缺口

`soak30.json` 的 broker 侧字段全为 0:

```
broker_cpu_cores 0, broker_pid 0, broker_rss_avg_mb 0,
broker_rss_peak_mb 0, broker_threads_peak 0
```

`loadgen` 自带的说明写明: 这需要 `-pid` 参数且 `/proc` 可读。实际运行时未传
`-pid`, 所以这些字段为零。本报告的 broker 侧数据 (第 4 节) 来自独立采集,
补上了这个缺口。

**下次运行应传 `-pid <broker pid>`**, 这样资源数据由工具直接记录, 不需要
事后补采。

## 5. 综合评估

### 5.1 达标情况

| 维度 | 结果 |
|---|---|
| 错误 | **0** (3,600 万次发送, 3.6 亿次接收) |
| 速率达成 | 99.96% |
| 投递完整性 | received/sent = 10.000, 精确匹配订阅者数量 |
| 内存 (生成端 9h) | 恒定 90 MB |
| 内存 (broker 9h) | +0.34%, 平稳 |
| 线程数 | 全程 11, 未增长 |
| 连接回收 | 5 秒内完全归零 |
| 关闭 | 干净响应 SIGTERM |

### 5.2 这些数字说明什么

**零错误且投递比精确为 10.0** 是本次最有说服力的两个数字。3.6 亿次投递中
没有一次重复或丢失, 说明 broker 的订阅关系管理在 2000 连接、100 并发发布者
的规模下是精确的, 不存在竞态导致的重复投递。

**连接回收的干净程度超出预期**。生成端被硬停, broker 仍在 5 秒内回收全部
2110 个会话。这意味着 broker 的资源回收不依赖对端配合 -- 这在生产环境中很
重要, 因为真实世界的客户端断线方式远比测试工具多样。

**9 小时内存平稳**排除了最常见的长期运行担忧。Go 运行时不会主动把堆归还
给操作系统, 所以 RSS 不回落是正常的; 关键是它没有增长。

### 5.3 不能由本次数据得出的结论

- **延迟长尾行为**: 30 分钟的 p999 已达 12 ms 且样本触顶, 9 小时的长尾
  分布未知。长时间运行下的内存型延迟累积 (例如 GC 压力) 未被观测。
- **MQTT QoS 1 的重传与持久会话**: 配置里 QoS 1 占 30%, 但本次没有断线
  重连场景, QoS 1 的重传路径未被验证。
- **broker 重启后的会话恢复**: clean session 与持久会话的行为未测。
- **2000 连接以上的规模**: 只测了 2000 这一个点。
