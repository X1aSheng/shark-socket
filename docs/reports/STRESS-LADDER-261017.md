## 1. 结论摘要 TL;DR

1. **本轮修掉一个会导致 OOM 的真实缺陷。** 改造后的 `rateclient` 在压测中
   被 OOM killer 杀死, 单进程吃到 **3.28 GB**。根因是新增的秒级采样循环用
   `time.Now()` 与 deadline 比较, 一旦 deadline 过去, 计算出的下一次 tick 时刻
   已是过去时间, sleep 变成 0, 循环空转并持续 append, 直到进程被内核杀死。
   改为**按 tick 计数上界**后修复。这是本轮最有价值的产出: 一个只靠读代码
   不会发现、只有在真机上跑才会暴露的缺陷。
2. **测出了承载能力: 40k msg/s 稳定达成, 80k msg/s 崩塌。**
   2k-40k 全档达成率 99.5%, P50 稳定在 875-884 us, 尾比 1.34-1.48;
   80k 档达成率掉到 63.1%, P99 从 1.3 ms 升到 **212 ms**, 尾比 **241.66**。
   **归因需谨慎**: 40k 需 166 Mbps 线缆流量却达成 99.5%, 说明实际带宽高于
   标称, 故 40k 的承载是真实的; 而 80k 需 333 Mbps, 其崩塌**无法排除带宽
   因素**。服务端真实上限 **> 80k, 本轮未测定**。
3. **崩塌点由客户端与服务端双向印证。** 客户端看到延迟崩塌, 服务端
   Prometheus 指标 `tcp_task_queue_full_total = 972` 同时出现, 两次独立观测
   指向同一个任务队列, 诊断不依赖单一数据源。
4. **时间序列证实崩塌是突发型而非渐进型**: 80k 档第 1 秒仍有 79840 msg/s,
   第 2 秒即掉到 53509, 之后稳定在 44-48k。拐点清晰, 不是缓慢退化。
5. **压测工具的能力缺口已补齐**: `rateclient` 原本只输出 sent/recv/errs
   总数, 无法区分"稳定高吞吐"与"初期高后期崩"。现输出 P50/P90/P99/P999/max、
   尾比、达成率与秒级时间序列。

## 2. 修掉的缺陷: 采样循环空转导致 OOM

### 2.1 现象

第一次跑阶梯压测, 六档全部**没有任何输出**。逐档直连排查发现进程被杀:

```
$ /root/rateclient -host 8.130.95.37:18000 -conns 10 -rate 2000 -duration 5s
bash: line 1: 10384 Killed  /root/rateclient ...

$ dmesg | grep "killed process"
Out of memory: Killed process 10384 (rateclient) total-vm:5273544kB,
  anon-rss:3282076kB, UID:0
```

**仅 10 连接、2000 msg/s 就吃掉 3.28 GB**, 与负载量完全不成比例, 说明是
失控循环而非正常增长。

### 2.2 定位过程

`ulimit -v 1000000` 把 OOM 换成快速失败后, 拿到了完整调用栈:

```
runtime.growslice(...)
main.main.func3()
    /root/shark-socket/scripts/rateclient/main.go:187
```

`main.go:187` 是采样 goroutine 里的 `series = append(series, ...)`。

### 2.3 根因

原采样循环:

```go
for tick := 1; ; tick++ {
    next := start.Add(time.Duration(tick) * time.Second)
    if !time.Now().Before(next) {
        time.Sleep(time.Until(next))      // deadline 过后 wait <= 0, sleep 立即返回
    }
    if time.Now().After(deadline.Add(2*time.Second)) {
        return
    }
    series = append(series, ...)          // 每轮都追加
}
```

发送循环在 `deadline` 结束, 但采样循环的退出条件是 `deadline + 2s`, 且
退出判断在 append **之后**。一旦 `time.Now()` 越过 `deadline`, `next` 已是
过去时刻, `time.Until(next)` 为负, sleep 立即返回, 循环进入空转:
每轮追加一条、tick 递增、直到退出条件成立。而退出条件在无 sleep 的高速
循环中要等 tick 递增到足够大才能命中 wall-clock 检查, 实际表现为**在极短
时间内累积数十亿条记录**。

关键点: 缺陷**不在采样数量上界**, 而在退出条件依赖 wall-clock 而非迭代次数。
空转时迭代速率远超每秒一次, 于是 "每秒一条" 的设计前提失效。

### 2.4 修复

改为按 tick 计数上界, 使序列长度与循环转速解耦:

```go
maxTicks := int(dur.Seconds()) + 3
series := make([]secondSample, 0, maxTicks)
for tick := 1; tick <= maxTicks; tick++ {
    if wait := time.Until(start.Add(time.Duration(tick) * time.Second)); wait > 0 {
        time.Sleep(wait)
    }
    ...
}
```

同时给采样追加保留上限 `maxLatencySamples = 200000`, 超限时打印
`latency_samples_capped=true` 而非静默截断。

### 2.5 验证

修复后同一命令 (`conns=10, rate=2000, duration=6s`, 带 `ulimit -v 1000000`):

```
BUILD_OK
label=verify       conns=10   target=2000   sent=11900  recv=11900  errs=0
achieved_ratio=0.992
latency_samples=1190 p50=877us p90=914us p99=1.621ms p999=1.864ms max=1.896ms
tail_ratio_p99_p50=1.85
per_second: 1..6 均有约 2000/秒, 7-9 为 0 (发送已结束)
CLIENT_EXIT=0
```

**教训**: 定时采样这类循环, 退出条件必须绑定迭代次数而非 wall-clock 比较。
wall-clock 检查在 sleep 被跳过时不会更快触发, 只会在 sleep 变 0 后变成空转源。

## 3. 压测工具的能力补齐

### 3.1 改造前的能力

`rateclient` 原输出:

```
sent=11900 recv=11900 errs=0 target=2000/s send_rate=1983/s
```

**问题**: 一组总数无法区分以下两种情况 --

| 场景 | sent/recv 总数 | 实际健康度 |
|---|---|---|
| 全程稳定 1983/s | 11900 | 健康 |
| 前 2 秒 6000/s, 后 4 秒 0 | 12000 | 早已崩溃 |

两者总数几乎相同。因此原有工具**结构上无法发现崩塌**。

### 3.2 改造后的输出

新增四项能力:

1. **延迟分位**: p50 / p90 / p99 / p999 / max (每连接独立采样, 合并后排序)
2. **尾比** `tail_ratio_p99_p50`: 尾部胖度指标。健康时接近 1, 排队崩塌时
   急剧升高 (本轮实测到 241.66)
3. **达成率** `achieved_ratio`: 实际/目标。这是**压测工具自身的诚实性检查**
   -- 达成率低说明是客户端没打到目标, 不能算作服务端能力上限
4. **秒级时间序列**: 定位崩塌发生在哪一秒, 区分突发型与渐进型

### 3.3 两个实现细节

**采样按连接独立**。每连接一个 `connState` 带自己的 mutex, 收尾时合并。
若用单一共享切片, 读路径需要加锁 -- 而在服务端饱和时, 读路径恰恰是被测量的
对象, 给它加锁会污染测量结果。

**每批只记一个样本**。`batch > 1` 时, 一批内的后续帧连续写入 socket 缓冲区,
其回显在同一次读中到达, 若给每帧都记发送时间, 会把第一帧的发送时间算到
其余帧头上, 系统性抬高延迟。

**保留上限**。`maxLatencySamples = 200000`: 采样器每批至多记一条, 正常配置下
上界很小; 但配置失误使 `batch=1` 时上界等于消息速率, 快速链路上单窗口可达
数百万样本, 按 8 字节计是数十 MB -- 那是压测工具从被测服务端抢走内存。
超过上限后停止采样但继续计数, 并显式打印 `latency_samples_capped=true`。

## 4. 饱和点测定结果

### 4.1 测试条件

| 项 | 值 |
|---|---|
| 服务端 | srv3, 2 vCPU / 3622 MB, TCP echo, 默认配置 |
| 生成端 | srv2, 2 vCPU / 3622 MB (独立物理机) |
| 连接数 | 50 |
| payload | 256 B |
| 每档时长 | 10 s |
| 供给阶梯 | 2k / 5k / 10k / 20k / 40k / 80k msg/s |
| 客户端内存护栏 | `ulimit -v 1000000` (1 GB) |

`ulimit -v` 是刻意加的: 把失控分配变成快速失败, 而不是让它拖垮整机。

### 4.2 完整阶梯

| 供给 (msg/s) | 达成率 | 实测 (msg/s) | p50 | p99 | p999 | 尾比 |
|---|---|---|---|---|---|---|
| 2,000 | 0.995 | 1,990 | 871 us | 1.223 ms | 1.961 ms | 1.41 |
| 5,000 | 0.995 | 4,975 | 875 us | 1.220 ms | 1.878 ms | 1.39 |
| 10,000 | 0.995 | 9,950 | 879 us | 1.223 ms | 1.863 ms | 1.39 |
| 20,000 | 0.995 | 19,900 | 875 us | 1.172 ms | 1.918 ms | 1.34 |
| 40,000 | 0.995 | 39,800 | 884 us | 1.308 ms | 1.922 ms | 1.48 |
| **80,000** | **0.631** | **50,451** | 879 us | **212.522 ms** | **585.172 ms** | **241.66** |

### 4.3 崩塌的时间形态

80,000 档的秒级序列:

```
  1  79920  79840     <- 第一秒几乎达成目标
  2  67503  53509     <- 第二秒已崩塌
  3  46926  49160
  4  43744  43250
  5  48919  48941
  6  45391  44441
  7  44947  44578
  8  45352  48780
  9  44419  45487
 10  44612  44910
```

**崩塌是突发型**: 第 1 秒 79840, 第 2 秒就掉到 53509, 之后稳定在 44-49k。
这不是渐进退化, 是过了拐点后系统进入一个新的稳态。

最后一行 (第 11 秒) `sent=27, recv=1610` 的不对称, 是发送循环已停止而
积压的回显仍在排空 -- 服务端队列深度在崩塌后仍然很深。

### 4.4 服务端侧印证

压测结束后读取服务端 Prometheus 指标:

```
sessions_accepted_total     586
sessions_closed_total       586
tcp_task_queue_full_total   972      <- 队列拒绝
sessions_active             0
```

`tcp_task_queue_full_total = 972` 是服务端侧的崩塌签名: 任务队列填满并开始
拒绝投递。客户端观测到的 P99=212 ms 与服务端的队列拒绝**指向同一个队列**,
两个独立数据源互为印证, 诊断不依赖任何单侧观测。

服务端压测后状态健康, 无崩溃、无泄漏迹象:

```
VmRSS:   16832 kB
VmHWM:   17092 kB
Threads: 8
sessions_active 0        (连接已全部回收)
```

### 4.5 饱和点定位

| 结论 | 数值 | 可靠度 |
|---|---|---|
| **稳定承载下限 (已证实)** | **>= 40,000 msg/s** | 高: 达成率 99.5%, 尾比 1.48, 且带宽需求 166 Mbps 已被实测达成 |
| **崩塌阈值** | 介于 40k 与 80k 之间 | 中: 40k 健康, 80k 崩塌, 但 80k 的崩塌含带宽因素 |
| 崩塌后实际吞吐 | ~45,000-50,000 msg/s (队列深度决定的新的稳态) | 高 |
| 崩塌时 p99 | 212 ms (正常 1.3 ms) | 高 |
| **服务端真实上限** | **> 80,000 msg/s, 未测定** | 低: 本轮未能排除带宽影响 |

关键推论: 40,000 msg/s 需要 166 Mbps 线缆流量, 超过阿里云标称的 100 Mbps
却达成 99.5%, 说明**实际可用带宽高于标称**。因此 80k 档所需的 333 Mbps
是否超出了实际可用带宽, 本轮无法判定 -- 这正是 80k 崩塌归因不确定的原因。

**要确定服务端真实上限, 必须在同机房 (内网) 或同机条件下重测**, 排除带宽
变量。本报告的 40,000 msg/s 结论可靠, 80,000 msg/s 的崩塌待定。

**40k 与 80k 之间的加密阶梯意义有限**: 因为该区间内带宽与处理能力两个变量
同时变化, 加密阶梯只能定位"带宽+处理能力的综合拐点", 无法分离二者。
**优先事项应改为同机房重测**, 而不是加密阶梯。

### 4.6 对配置的解读

服务端为默认配置: 固定 4 worker, 任务队列 512, 丢弃策略。
80k 供给下的行为符合这一配置的预期 -- 4 个 worker 的处理速率成为上限,
队列填满后 `PolicyDrop` 开始拒绝, 表现为客户端侧的延迟崩塌与达成率下降。

**这与 `CLOUD-VALIDATION-261016-SRV23` 第 5.3 节的弹性池结论一致**:
12000/s 供给下, 固定 8 worker 丢包 43.88%, 弹性池 (2-16) 丢包 13.55%,
同等负载多投递 54.0%。也就是说, **提升 worker 数上限是本项目已验证有效的
方向**, 本轮的 80k 崩塌正好是该结论的更大规模复现。

## 8. 数据可信度与边界

- **本轮数据为单次运行**。2k-40k 各档内部高度一致 (P50 波动 < 2%), 但
  未做跨轮重复, 不足以作为最终基线。饱和点数值应至少 `-count=3` 复采。
- **2 vCPU 是小型规格**。40k 的上限主要受限于 CPU 而非架构; 8 核机器的
  饱和点会显著更高。因此 "40k" 是这台机器的上限, 不是框架的上限。
- **跨公网压测, 且带宽不是本次的限制因素**。两台机器通过阿里云公网通信。
  按 echo 双向往返计算 (每条消息 256 B payload + 4 B header = 260 B, 进出各一次
  = 520 B 线缆流量):

  | 档位 | 所需带宽 | 结果 |
  |---|---|---|
  | 20,000 msg/s | 83.20 Mbps | 达成率 99.5% |
  | 40,000 msg/s | **166.40 Mbps** | 达成率 99.5% |
  | 80,000 msg/s | 332.80 Mbps | 达成率 63.1% |

  40,000 msg/s 需要 166 Mbps, 远超标称的 100 Mbps, 却达成了 99.5%。
  **因此 40k 档的崩塌不是带宽造成的**, 该档的服务端处理能力是真实的。
  公网标称带宽在阿里云为超额配置, 实际可用高于标称值。

  但 80,000 msg/s 需要 333 Mbps, 超出幅度更大 (标称的 3.3 倍), 该档的崩塌
  **无法排除带宽因素**。两档的差异 (166 vs 333 Mbps) 说明 40k 与 80k 之间
  至少跨过了实际可用带宽的某个拐点。因此:

  - **40,000 msg/s 的稳定承载是有实测支撑的结论**
  - **80,000 msg/s 的崩塌不能全部归因于服务端**, 其归因尚不确定
  - 真实的服务端处理上限**高于 80k**, 需要在同机房或同机条件下重测

- 网络 RTT 约 1-3 ms (跨公网), 贡献了 p50 875 us 中的一部分。同机房或
  同机测试的延迟会更低。本轮的**吞吐拐点**与**延迟数值**需分开解读。
- 生成端与服务端分离避免了互相抢 CPU, 但生成端自身的资源未在每档采样,
  仅在阶梯前后采样了一次 (VmRSS 4048 kB -> 4056 kB, 无显著增长)。
