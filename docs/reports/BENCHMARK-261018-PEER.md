# 同机对等基准: shark-socket vs gnet vs cloudwego/netpoll

## meta-info

- 报告编号: BENCHMARK-261018-PEER
- 日期: 2026-10-18
- 任务: 关闭 `COMPARISON-261018-OSS-PEERS` 的 E1 (缺同机横向基准)
- 代码基线: `tests/peerbench` (嵌套 module, `replace` 指向工作树, 不测 tag)
- 拓扑: **同机**。服务端与客户端跑在同一台云主机上, srv2 (8.130.182.119) 与
  srv3 (8.130.95.37) 各跑一遍, 两次互不相干
- 环境: Ubuntu 26.04, 2 vCPU / 4 GB, go1.26.9 linux/amd64,
  gnet v2.10.0, cloudwego/netpoll v0.7.5
- 驱动: `tests/peerbench/run.sh`, 客户端 `tests/peerbench/cmd/load` (四臂共用)

---

## 1. 结论摘要 TL;DR

1. **单连接是唯一没被客户端压垮的档位, 本项目在这里落后 1/3。**
   1 连接 / pipeline 16: 本项目 216-234k msg/s, gnet 339-344k, netpoll 306-311k
   → 落后 gnet **32-36%**, 落后 netpoll **25-29%**。单次往返 (pipeline 1)
   p50 **12 us vs 9 us (gnet) / 10-11 us (netpoll)**, 速率 67-69k vs 99-101k。
2. **差距不在 handler。** 同一负载下 `handler_duration_seconds` 均值
   **0.65 us/条** (n = 1,135,082, 总和 0.739 s), 其中 97.1% 的调用 ≤1 us。
   12 us 的往返里业务代码只占 5%, 剩下的在 dispatch 与 socket 路径上。
3. **B2 的写缓冲只补回一小部分。** 同一二进制加 `-write-buffer 4096`:
   1 连接 **+6% ~ +12%**, 16 连接 +1%, 64 连接 0%, 单次往返 -1%。
   逐帧 write syscall 是真实开销, 但不是这 1/3 的主项。
4. **16/64 连接四臂收敛, 排序不可信。** 16 连接时本项目与 gnet 打平
   (0-2%), 64 连接时反超 gnet 9-11% 但仍落后 netpoll 5-7%。
   2 vCPU 上客户端与服务端共享核, 四臂都挤在 418-518k msg/s 这个带上,
   这一带是**客户端的天花板**, 不是服务端的排序。
5. **结论方向: 这不是推翻 2.2 节的"不并列数字", 而是把它具体化。**
   同一台机器、同一个客户端、同一种 echo 之下, 专职传输内核在本项目最强项的
   相邻形态上领先 1/3; 本项目换来的是队列背压、8 种协议、连接生命周期与插件隔离。
   把这两个事实同时写下来, 比只写其中一个更接近真实。

## 2. 方法: 为什么必须同机、同客户端、同 echo

- **同机**: 跨机对比量的是网络与两台机器的差异; 同机至少让"同一时刻的同一台机器"
  成为共同前提, 代价是客户端与服务端抢两个核 (见第 5 节)。
- **同一个客户端二进制**: 三个服务端由同一个 `cmd/load` 驱动。换客户端就等于换
  量具, 而换量具之后任何差异都无法归因。
- **同一种负载**: 定长 256 B 字节 echo, 不管帧头。三家的 framing 实现完全不同
  (长度前缀解析 / ring buffer peek / nocopy LinkBuffer), 把三种解析器放进比较,
  测到的是解析器而不是 IO 路径。
- **每条连接首字节打标并回验**: 服务端一旦混流, 客户端直接判失败而不是出一个数。
- **两相**: 吞吐 (1/16/64 连接, pipeline 16) 与延迟 (`-rtt`: 1 连接, pipeline 1)。
  深流水行的延迟列是排队时间, 不是往返时间 -- 读开始的时候 echo 往往已经在
  缓冲区里了, 所以两相分开跑。
- **每档 3 轮取中位数**, 两轮之间无重叠区间才在本文中引用 (第 3 节表格里
  最小/最大值可见)。
- **只允许 Linux**: netpoll v0.7.5 的 `netpoll_windows.go` 里 `NewEventLoop`
  直接返回 `(nil, nil)`, Windows 上没有事件循环; 且本机单调时钟 tick 约 0.5 ms,
  93% 的亚毫秒往返会被采成 0 (实测 p50 = 0, p99 = 538 us)。

## 3. 结果

### 3.1 吞吐 (msg/s, 每档 3 轮中位数)

| arm | 1 连接 srv2 / srv3 | 16 连接 srv2 / srv3 | 64 连接 srv2 / srv3 |
| --- | --- | --- | --- |
| shark | **216.0k / 233.9k** | 418.0k / 429.5k | 481.2k / 493.6k |
| shark-wb (写缓冲 4096) | **242.0k / 248.3k** | 421.1k / 432.6k | 482.9k / 489.8k |
| gnet | **339.3k / 343.7k** | 428.7k / 429.8k | 440.7k / 444.3k |
| netpoll | **306.0k / 310.7k** | 472.4k / 471.3k | 517.7k / 517.5k |

相对本项目 (shark 行为基准):

| 档位 | vs gnet | vs netpoll | 写缓冲收益 |
| --- | --- | --- | --- |
| 1 连接 | -36% / -32% | -29% / -25% | +12% / +6% |
| 16 连接 | -2% / 0% | -12% / -9% | +1% / +1% |
| 64 连接 | +9% / +11% | -7% / -5% | 0% / -1% |
| 单次往返 (`-rtt`) | -33% / -32% | -18% / -16% | -1% / -1% |

### 3.2 单次往返延迟 (1 连接, pipeline 1, p50 / p99, us)

| arm | srv2 | srv3 |
| --- | --- | --- |
| shark | 12 / 30 | 12 / 29 |
| shark-wb | 12 / 30 | 12 / 30 |
| gnet | **9 / 18** | **9 / 18** |
| netpoll | 10 / 23 | 11 / 23 |

### 3.3 把 12 us 拆开: handler 占多少

1 连接 / pipeline 16 / 10 s, 从本项目自己的 `/metrics` 端点读:

| 指标 | 值 |
| --- | --- |
| `messages_total{protocol="tcp"}` | 1,135,082 |
| `handler_duration_seconds_sum` | 0.739 s |
| **均值** | **0.65 us / 条** |
| 分位 (直方图桶) | ≤1 us: 97.1%, ≤2.5 us: 98.5%, ≤5 us: 99.0%, ≤10 us: 99.3% |

即: 单连接往返 12 us 中, 用户 handler (一次 `sess.Send`) 占 0.65 us。
剩下 11 us 分摊在读取、分帧、任务投递、工作池唤醒与写回上, 客户端侧的成本也
包含在内 (同机, 无法分离) -- 所以能说的是**差值**, 不是绝对值。

## 4. 归因: 差距在哪一跳

三家服务端在同一条机器上的结构差异只有一个: 消息由谁交给 handler。

- gnet: reactor goroutine 内联调用 `OnTraffic`, 处理与读写同一个 loop。
- netpoll: poller 里的 `OnRequest`, 同样是内联。
- 本项目: 每连接 2 goroutine 读取, 每帧投递到工作池队列, 由 worker 执行 handler。

一帧多一次队列交接 (channel 发送 + 一次 goroutine 唤醒), 量级正是几个 us,
与实测 3 us 差值 (12 vs 9) 同量级。**但这是假设, 直接证据只有两条:**

1. handler 均值 0.65 us, 显然不是它 (3.3 节);
2. 写缓冲把 1 连接吞吐抬高 6-12%, 说明逐帧 syscall 是真开销, 但仍不足 1/3。

反证也有一条, 必须写出来: **如果每帧多一次交接是固定成本, 64 连接时它不会
消失**。64 连接本项目反超 gnet 9-11%, 这与"固定成本被平行摊薄"矛盾, 更像是
那个档位四臂一起撞上了客户端的墙 (418-518k 的窄带, 且两台的排序不一致)。

因此本文对归因的立场是: **单连接的 1/3 差距是可复现的测量结果, 具体落在
"投递 + socket"这一段是推断, 尚未逐项拆开。** 要拆开需要下一步实验
(见第 7 节), 现在不该在文档里写成结论。

---

## 5. 可信度与威胁

- **客户端与服务端同机, 2 vCPU 共享。** 绝对数字不是容量承诺; 16/64 连接行
  极可能是客户端先饱和。1 连接行受此影响最小, 也是本文唯一用来断言排序的档位。
- **换行/协议无关。** 256 B 定长 echo 不测协议解析, 而协议解析正是本项目的
  主要工作量所在; 这张表衡量的是 IO 骨架, 不是"网关能力"。
- **对端配置**: gnet `WithMulticore(true)` (默认), netpoll 默认, 本项目默认
  (固定工作池, `WriteBufferBytes=0`); 每条 arm 的配置差异都写在 `run.sh` 里。
- **3 轮**: 表格里三行数字的极差普遍 <2%, 两次主机之间差距 <8%,
  排序在两次之间只有 64 连接行翻转。

## 6. 复现

```bash
# 云主机上 (Go 1.26.9, Linux)
cd tests/peerbench
bash run.sh                      # 4 臂 x 2 相 x 3 轮, 约 5 分钟
CONNS="1" DURATION=10s REPEATS=3 bash run.sh    # 只看单连接
```

单臂调试:

```bash
./bin/shark -addr 127.0.0.1:19001 -write-buffer 4096 -metrics 127.0.0.1:19100
./bin/load  -addr 127.0.0.1:19001 -conns 1 -size 256 -pipeline 16 -duration 10s
curl -s 127.0.0.1:19100/metrics | grep handler_duration_seconds
```

环境注意: 云主机上需要 `PATH=/usr/local/go/bin:$PATH` 与
`GOPROXY=https://goproxy.cn,direct` (直连 proxy.golang.org 会超时)。

## 7. 要不要动单连接路径

| 方案 | 动作 | 收益 | 代价 | 判断 |
| --- | --- | --- | --- | --- |
| A. handler 可在读取 goroutine 内联执行 | 新增 server 选项, 运行期二选一 | 预计吃掉 1/3 差距的大部分 (未测) | 失去队列背压与 worker 隔离; 慢 handler 直接堵住读取, 违背现有限流设计 | 不建议默认, 可作为选项 |
| B. 加大 `RawFramer` 单帧上限 / 读取批量 | 调参, 少数几行 | 1 连接 +6-12% (已测: 写缓冲同等量级) | 帧变大意味着单条慢消息占用更多内存 | 已在 `WriteBufferBytes` 覆盖, 不重复做 |
| C. 保持现状, 把差距写进文档 | 无 | 读者有准确预期 | 无 | **当前选择** |

判断依据: 本项目的目标形态是多协议网关 (几十到几万条长连接), 单连接极限吞吐
不是它要赢的赛道; 而 A 的代价正好是它要卖的东西 (背压与隔离)。真正该先做的是
把差距**说清楚**, 也就是这份报告和 `COMPARISON-261018-OSS-PEERS` 2.2 节的更新。

若后续有单连接场景的真实需求 (例如每连接一条大流量的隧道), 再按 A 做一次
带 ADR 的实验, 并用本报告的表格作为基线。
